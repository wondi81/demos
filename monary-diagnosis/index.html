SEC-01

자녀 거래내역 테이블에 행 단위 보안 정책이 빠져 있음

보안 · Supabase RLS
치명
증상

로그인한 아무 부모 계정이 공개 키만으로 다른 가족의 용돈 거래내역을 조회할 수 있습니다. 앱 화면에서는 보이지 않지만 API를 직접 부르면 열립니다.

재현 절차
  1. 시험 가족 A, B 계정 생성
  2. A 계정 토큰으로 transactions 테이블 조회
  3. B 가족 행이 함께 반환되는지 확인
근거
-- 현재: RLS는 켜져 있으나 SELECT 정책이 모두 허용
alter table transactions enable row level security;
create policy "read all" on transactions for select using (true);

-- 수정안: 같은 가족 구성원만 조회
create policy "family read" on transactions for select
  using (family_id in (
    select family_id from family_members where user_id = auth.uid()
  ));
수정안

전 테이블의 정책을 표로 뽑아 허용 범위를 확인하고, 가족 단위 정책으로 교체합니다. 관리자 기능은 서비스 키를 쓰는 서버 함수로만 남기고, 수정 후 시험 계정으로 교차 조회가 막히는지 다시 확인합니다.

예상 공수 3일개선 견적 120만원재검증 포함
FIN-02

용돈 지급과 이자 정산이 동시에 돌면 잔액이 덮어써짐

기술·기능 · 금융 데이터 정합성
치명
증상

매월 1일 이자 정산 작업과 부모의 수동 용돈 지급이 몇 초 차이로 겹치면 한쪽 금액이 사라집니다. 거래 기록은 두 건인데 잔액은 한 건만 반영됩니다.

재현 절차
  1. 시험 계정 잔액 10,000원
  2. 이자 정산과 지급 5,000원을 동시에 20회 호출
  3. 최종 잔액과 거래 합계 비교 (가상 결과: 20회 중 6회 불일치)
근거
// 현재: 읽고 계산한 뒤 덮어쓰기 (두 요청이 같은 값을 읽음)
const { balance } = await getWallet(childId)
await updateWallet(childId, { balance: balance + amount })

-- 수정안: DB 함수 안에서 한 번에 더하고 기록 (원자적 처리)
update wallets set balance = balance + p_amount
 where child_id = p_child returning balance;
수정안

잔액 변경은 모두 DB 함수 하나로 모으고, 거래 기록과 잔액 갱신을 같은 트랜잭션에 묶습니다. 정산 작업에는 중복 실행 방지 키를 붙이고, 거래 합계와 잔액이 맞는지 매일 대조하는 점검 쿼리를 남깁니다.

예상 공수 2.5일개선 견적 100만원동시 호출 시험 포함
PAY-03

결제 웹훅이 서명 확인 없이 처리되고, 같은 알림이 두 번 오면 두 번 충전됨

결제·구독 · PortOne 웹훅
높음
증상

결제사는 응답이 늦으면 같은 웹훅을 다시 보냅니다. 현재는 재전송마다 충전이 새로 일어나고, 서명을 보지 않아 외부에서 위조한 요청도 받아들입니다.

재현 절차

  2. 같은 웹훅 본문을 두 번 전송

만 14세 미만 자녀 가입에 법정대리인 동의 기록이 없고, 탈퇴 후 자녀 데이터가 남음

03 인프라 판단

Supabase 유지 vs 별도 백엔드

취향이 아니라 아래 조건을 하나씩 확인해서 정합니다. "아니오"가 늘어날수록 별도 백엔드 쪽으로 기웁니다.

  • 예
    모든 테이블의 접근 권한을 RLS 정책으로 표현할 수 있는가
    SEC-01 수정 후
  • 예
    금액이 바뀌는 처리를 DB 함수 하나로 원자적으로 묶을 수 있는가
    FIN-02
  • 예
    결제 웹훅·정산처럼 서버에서만 돌아야 할 로직이 서버 함수 안에 들어가는가
    PAY-03
  • 예
    예상 사용자 규모에서 DB 연결 수와 응답 시간이 요금제 한도 안인가
    부하 측정
  • 아니오
    제휴 금융사가 요구하는 망 분리·접속 기록 보관을 현재 구성으로 증빙할 수 있는가
    제휴 조건 확인
  • 예
    백업·복구 시점을 운영자가 직접 지정하고 시험 복구해 볼 수 있는가
    복구 리허설

판정 (가상)

Supabase 유지, 금전 이동 구간만 분리 검토
여섯 조건 중 다섯이 충족되어 지금 전면 이전할 근거는 약합니다. 제휴 금융사의 보안 요구가 확정되면 그 구간만 별도 서버로 떼는 안을 비교합니다.

실제 보고서에서는 각 조건 옆에 측정값과 확인한 화면·쿼리를 근거로 붙입니다.
